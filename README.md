# CandidAI

Бекенд-система автоматизації первинного рекрутингу на базі Spring Modulith. Система забезпечує повний життєвий цикл вакансій, прийом заявок кандидатів, ШІ-скринінг резюме, збір фідбеків інтерв'ю та автоматичні сповіщення.

## Архітектурні модулі

Проєкт побудований як модульний моноліт (Spring Modulith). Кожен модуль є ізольованим пакетом із публічним API та інкапсульованою внутрішньою логікою:

* `vacancy` - керування вакансіями, їх параметрами та статусами.
* `recruitment` - прийом заявок, воронка відбору кандидатів, інтерв'ю-фідбеки та стратегії оцінювання.
* `assessment` - автоматичний ШІ-скринінг резюме через Google Gemini API.
* `notification` - асинхронне відправлення повідомлень кандидатам та авторам вакансій (Email, Telegram).
* `user` - профілі користувачів, ролі (CANDIDATE, RECRUITER, ADMIN) та налаштування каналів зв'язку.
* `common` - спільні доменні винятки, валідатори, генератори і глобальна обробка помилок (RFC 9457).

## Бізнес-правила

### 1. Вакансії (`vacancy`)
* **Початковий статус**: Вакансію можна створити виключно у статусі `DRAFT` або `OPEN`. Якщо статус не вказаний у запиті, за замовчуванням встановлюється `OPEN`. Будь-який інший початковий статус відхиляється (`422 Unprocessable Entity`).
* **Унікальність**: Заборонено створення двох активних вакансій з однаковою назвою для одного автора (`(authorId, title)`). При порушенні повертається `409 Conflict`.
* **Зарплатна вилка**: Якщо вказані обидві межі зарплати (`salaryMin` і `salaryMax`), значення `salaryMin` не може перевищувати `salaryMax`. Порушення викликає помилку валідації (`400 Bad Request`).
* **Фіксація дати публікації**: При створенні у статусі `OPEN` поле `publishedAt` встановлюється в поточний час. При створенні `DRAFT` поле залишається `null`. При переході з `DRAFT` у `OPEN` дата `publishedAt` автоматично фіксується поточним часом.
* **М'яке видалення (Soft Delete)**: Видалення вакансії встановлює прапорець `deleted = true` і фіксує `deletedAt`. Видалена вакансія стає недоступною для перегляду, редагування та подачі нових заявок (`404 Not Found`).
* **Події**: Будь-яка зміна статусу публікує доменну подію `VacancyStatusChangedEvent`.

### 2. Заявки кандидатів (`recruitment`)
* **Умова подачі**: Заявка приймається лише на існуючу та відкриту вакансію (`status == OPEN`). Подача на закриту чи відсутню вакансію повертає `404 Not Found`.
* **Запобігання дублікатам та редагування**: Кандидат з одним і тим самим email не може подати нову заявку на ту саму вакансію повторно (`(vacancyId, email)` є унікальною парою). Проте кандидат має можливість переглянути та відредагувати контактні дані (номер телефону, посилання на резюме) у раніше поданій заявці, поки вона знаходиться у початковому статусі `APPLIED`. Після переходу на наступні етапи відбору редагування блокується.
* **Міжнародна валідація контактів**: Номер телефону підтримує міжнародні формати стандарту ITU-T E.164 (від 7 до 15 цифр, наприклад `+380 50 123 45 67`, `+1 (555) 123-4567`).
* **Початковий стан заявки**: Завжди `APPLIED`.
* **Асинхронний тригер**: При успішній реєстрації публікується подія `ApplicationSubmittedEvent`, яка ініціює асинхронний ШІ-скринінг резюме.

### 3. Оновлення статусу заявки
* **Контроль переходів**: Зміна статусу підпорядковується суворій матриці станів. Невалідний перехід блокується помилкою `InvalidStateTransitionException` (`422 Unprocessable Entity`).
* **Обов'язковий коментар при відхиленні**: Переведення заявки у статус `REJECTED` вимагає обов'язкового непустого коментаря з причиною відмови. Порушення валідується на рівні DTO (`400 Bad Request`).
* **Захисний бар'єр для OFFER**: Перехід у статус `OFFER` автоматично запускає оцінювання кандидата за фідбеками інтерв'ю. Якщо результат оцінювання - `REJECT`, перехід у статус `OFFER` відхиляється (`422 Unprocessable Entity`).
* **Події**: Кожна зміна статусу публікує `ApplicationStatusChangedEvent`.

### 4. Інтерв'ю та відгуки
* **Контекст подачі відгуку**: Додати фідбек інтерв'юера (`POST /api/v1/applications/{id}/feedbacks`) можна лише у випадку, коли заявка перебуває у статусі `INTERVIEW`. Для будь-якого іншого статусу повертається `422 Unprocessable Entity`.
* **Параметри оцінки**: Кожен фідбек містить оцінку технічних навичок `technicalScore` (від 1 до 5) та вердикт `decision` (`HIRE` або `REJECT`).

### 5. Стратегії оцінки кандидатів (Candidate Evaluation)
Оцінка агрегується за результатами всіх збережених фідбеків для заявки. Конкретна стратегія обирається динамічно відповідно до категорії вакансії (`JobCategory`):

* **ENGINEERING**:
  * Середній технічний бал повинен бути не менше 4.0 (`averageScore >= 4.0`).
  * Повна відсутність негативних рішень (жоден інтерв'юер не повинен поставити `REJECT`).
  * При виконанні обох умов рекомендація - `HIRE`, інакше - `REJECT`.
* **MANAGEMENT**:
  * Середній технічний бал повинен бути не менше 3.5 (`averageScore >= 3.5`).
  * Сувора більшість позитивних голосів (`hireVotes > rejectVotes`).
  * При виконанні обох умов рекомендація - `HIRE`, інакше - `REJECT`.
* **DEFAULT (інші категорії)**:
  * Середній технічний бал повинен бути не менше 3.0 (`averageScore >= 3.0`).
  * При виконанні рекомендація - `HIRE`, інакше - `REJECT`.
* **Загальне правило для всіх категорій**: За відсутності жодного збереженого фідбеку результат оцінки завжди повертає вердикт `REJECT` з балом 0.0.

### 6. ШІ-скринінг резюме (`assessment`)
* **Автоматичний запуск**: Модуль слухає `ApplicationSubmittedEvent` через `@ApplicationModuleListener`.
* **Результат аналізу**:
  * Якщо кандидат пройшов перевірку (`passed == true`): статус заявки автоматично переводиться з `APPLIED` у `SCREENING`, записується `matchingScore`.
  * Якщо кандидат не відповідає вимогам (`passed == false`): статус переводиться у `REJECTED` із зазначенням причини у коментарі.
  * Якщо стався технічний збій інтеграції з ШІ (`status == FAILED`): статус заявки залишається `APPLIED` без змін, запит можна повторити вручну через контролер оцінювання.

## Матриці переходів станів (State Machines)

### 1. Життєвий цикл вакансії (`VacancyStatus`)

Схема переходів:
```text
           ┌──────────┐
           │  DRAFT   ├──────────────┐
           └────┬─────┘              │
                │                    │
                ▼                    │
           ┌──────────┐              │
     ┌────►│   OPEN   │◄───┐         │
     │     └────┬─────┘    │         │
     │          │          │         │
     │          ▼          │         │
     │     ┌──────────┐    │         │
     └─────┤  PAUSED  ├────┤         │
           └────┬─────┘    │         │
                │          │         │
                ▼          │         │
           ┌──────────┐    │         │
           │  CLOSED  ├────┘         │
           └────┬─────┘              │
                │                    │
                ▼                    ▼
           ┌───────────────────────────┐
           │         ARCHIVED          │
           └───────────────────────────┘
```

Таблиця переходів:

| Зі стану (From) \ В стан (To) | DRAFT | OPEN | PAUSED | CLOSED | ARCHIVED |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **DRAFT** | дозволено | дозволено | заборонено | заборонено | дозволено |
| **OPEN** | заборонено | дозволено | дозволено | дозволено | дозволено |
| **PAUSED** | заборонено | дозволено | дозволено | дозволено | дозволено |
| **CLOSED** | заборонено | заборонено | заборонено | дозволено | дозволено |
| **ARCHIVED** | заборонено | заборонено | заборонено | заборонено | дозволено |

Правила переходів:
* Перехід у той самий статус (`from == to`) вважається валідним і не змінює стан об'єкта.
* З `DRAFT` можна перейти лише у `OPEN` (публікація) або в `ARCHIVED`.
* З `OPEN` можна тимчасово призупинити набір (`PAUSED`), закрити набір (`CLOSED`) або архівувати (`ARCHIVED`).
* З `PAUSED` можна відновити публікацію (`OPEN`), закрити вакансію (`CLOSED`) або архівувати (`ARCHIVED`).
* З `CLOSED` доступний лише перехід у `ARCHIVED`.
* `ARCHIVED` - термінальний стан. Вихід з нього у будь-який інший статус заборонений.

### 2. Воронка відбору кандидата (`ApplicationStatus`)

Схема переходів:
```text
  ┌──────────┐
  │ APPLIED  ├───────────────────────────────┐
  └────┬─────┘                               │
       │                                     │
       ▼                                     │
  ┌──────────┐                               │
  │SCREENING ├─────────────────────────┐     │
  └────┬─────┘                         │     │
       │                               │     │
       ▼                               │     │
  ┌──────────┐                         │     │
  │INTERVIEW ├───────────────────┐     │     │
  └────┬─────┘                   │     │     │
       │                         │     │     │
       ▼ (якщо оцінка != REJECT) │     ▼     ▼
  ┌──────────┐                   │ ┌──────────┐
  │  OFFER   ├───────────────────┴►│ REJECTED │ (термінальний)
  └────┬─────┘                     └──────────┘
       │
       ▼
  ┌──────────┐
  │  HIRED   │ (термінальний)
  └──────────┘
```

Таблиця переходів:

| Зі стану (From) \ В стан (To) | APPLIED | SCREENING | INTERVIEW | OFFER | HIRED | REJECTED |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **APPLIED** | заборонено | дозволено | заборонено | заборонено | заборонено | дозволено |
| **SCREENING** | заборонено | заборонено | дозволено | заборонено | заборонено | дозволено |
| **INTERVIEW** | заборонено | заборонено | заборонено | дозволено* | заборонено | дозволено |
| **OFFER** | заборонено | заборонено | заборонено | заборонено | дозволено | дозволено |
| **HIRED** | заборонено | заборонено | заборонено | заборонено | заборонено | заборонено |
| **REJECTED** | заборонено | заборонено | заборонено | заборонено | заборонено | заборонено |

Правила переходів:
* Воронка є строго послідовною: не можна перестрибувати етапи (наприклад, з `APPLIED` одразу в `INTERVIEW` чи `OFFER`).
* Повернення на попередні етапи заборонене (наприклад, з `INTERVIEW` назад у `SCREENING`).
* Перехід у `REJECTED` дозволений з будь-якого незавершеного етапу (`APPLIED`, `SCREENING`, `INTERVIEW`, `OFFER`), але вимагає обов'язкового поля `comment` у запиті.
* Перехід `INTERVIEW -> OFFER` додатково верифікується: якщо результат стратегії оцінки кандидатів є `REJECT`, перехід блокується помилкою 422.
* Стани `HIRED` та `REJECTED` є кінцевими (термінальними). Будь-яка подальша зміна статусу з них неможлива.

## Формат помилок та статуси HTTP

Система повертає помилки за стандартом RFC 9457 (`ProblemDetail`):

* `400 Bad Request` - помилки валідації вхідних даних (некоректні поля запиту, відсутність обов'язкового коментаря при відхиленні заявки, порушення умови `salaryMin <= salaryMax`).
* `404 Not Found` - запитуваний ресурс не існує або був помічений як видалений.
* `409 Conflict` - спроба створення дубліката (повторна заявка кандидата на ту саму вакансію, повторна вакансія з однаковою назвою від одного автора, користувач з існуючим email).
* `422 Unprocessable Entity` - спроба невалідного переходу статусу у скінченному автоматі або блокування переходу бізнес-правилом (наприклад, оффер кандидату з негативним рішенням оцінювання).

## Веб-інтерфейс та безпека (Thymeleaf & Spring Security)

Система надає повнофункціональний серверний веб-інтерфейс на базі **Thymeleaf**, стилізований за допомогою локального **Bootstrap 5.3.3 (WebJar)** та захищений мультиланцюговою архітектурою **Spring Security**:

### 1. Три ланцюги фільтрів безпеки (`SecurityFilterChain`)
* **`@Order(1)` API Chain (`/api/**`)**: безсесійний захист (JWT Bearer tokens), вимкнений CSRF, повернення машинних помилок у форматі RFC 9457 `ProblemDetail` (401/403).
* **`@Order(2)` OpenAPI Chain (`/v3/api-docs/**`, `/swagger-ui/**`)**: публічний доступ до специфікації та Swagger UI з релаксованою політикою CSP для роботи скриптів документації.
* **`@Order(3)` Web Chain (браузерні маршрути)**: сесійна автентифікація (`formLogin` на `/login`), активний CSRF-захист, logout виключно через POST з CSRF, строгий CSP (`script-src 'self'`), сесійний контроль (`sessionFixation().migrateSession()`, `maximumSessions(1)`).

### 2. Ключові веб-сторінки та сценарії
* `/vacancies` - публічний реєстр активних вакансій із фільтрацією за статусом/категорією, перемиканням представлення (`TABLE` або `CARDS`) та локалізацією (`UA` / `EN`).
* `/vacancies/new` - захищена форма створення вакансії (`RECRUITER`, `ADMIN`) з валідацією JSR-380, перевіркою зарплатної вилки (`@ValidSalaryRange`) та патерном **Post-Redirect-Get (PRG)**.
* `/vacancies/{id}/apply` - форма подання або редагування збереженої заявки кандидатом (`CANDIDATE`) з автоматичним підтягуванням даних із профілю, міжнародною валідацією номера телефону та відображенням поточного статусу.
* `/vacancies/{id}/applications` - перегляд відгуків кандидатів та результатів AI-оцінювання (`TECH_LEAD`, `RECRUITER`, `ADMIN`).
* `/login` - власна сторінка входу з обробкою невірних облікових даних.
* `/error/403.html`, `/error/404.html`, `/error/5xx.html` - стилізовані сторінки помилок у загальному layout.

### 3. Тестові облікові записи (Argon2id)
* **Рекрутер**: `recruiter@candidai.com` / `RecruiterPass123!` (`ROLE_RECRUITER`)
* **Кандидат**: `candidate@candidai.com` / `CandidatePass123!` (`ROLE_CANDIDATE`)
* **Тімлід**: `techlead@candidai.com` / `TechLeadPass123!` (`ROLE_TECH_LEAD`)
* **Адміністратор**: `admin@candidai.com` / `AdminPass123!` (`ROLE_ADMIN`)
