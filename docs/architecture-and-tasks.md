# Архітектура CandidAI та розподіл завдань для команди

Цей документ простою мовою пояснює, як ми будуємо проєкт **CandidAI**, чому ми обрали **Spring Modulith** замість складної *Clean Architecture*, як модулі взаємодіють між собою та як ми ділимо завдання на трьох людей для виконання ДЗ.

---

## 1. Що таке CandidAI?
**CandidAI** — це бекенд-система автоматизації первинного рекрутингу для HR-фахівців та рекрутерів:
* **Вакансії:** Рекрутер створює вакансію з вимогами до навичок та зарплатною вилкою.
* **Подання заявки:** Кандидат подає заявку та прикріплює резюме (PDF/DOCX).
* **ШІ-скринінг:** Система автоматично зчитує резюме через LLM (Google Gemini / Spring AI), рахує `matchingScore` (відсоток відповідності вимогам) та генерує список адаптивних технічних питань.
* **Воронка відбору (State Machine):** Заявка рухається по етапах: `APPLIED -> SCREENING -> INTERVIEW -> OFFER / REJECTED`.
* **Технічне інтерв'ю:** Технічний лід оцінює кандидата за шкалою та залишає стандартизований відгук.
* **Автосповіщення:** Кандидат автоматично отримує листи/повідомлення в Telegram про кожен змінений статус.

---

## 2. Архітектура: Чому Spring Modulith і ЧОМУ БЕЗ Clean Architecture?

### Чому ми відмовилися від Clean Architecture?
У навчальних і реальних бізнес-проєктах *Clean Architecture* (чи *Hexagonal Architecture*) часто призводить до надмірного ускладнення (overengineering):
* На один звичайний ендпоінт доводиться писати по 6–8 класів: `CreateVacancyController`, `CreateVacancyInputPort`, `CreateVacancyUseCase`, `VacancyRepositoryOutputPort`, `VacancyDatabaseAdapter`, плюс 3 різних класи сутності та купу ручних маперів між ними.
* Код роздувається втричі, а реальної користі для нашого стеку це не дає.

### Як працює Spring Modulith?
**Spring Modulith (Модульний моноліт)** — це підхід, де весь проєкт запускається як **один звичайний Spring Boot додаток** (один JAR, один Gradle-проєкт), але всередині код розбитий на **ізольовані бізнес-модулі**.

Кожен модуль — це окремий Java-пакет верхнього рівня:
```text
ua.edu.ukma.candidai/
├── CandidAiApplication.java       <-- Головний клас Spring Boot
│
├── common/                        <-- Спільні речі (помилки, конфігурації)
│   └── exception/
│       └── GlobalExceptionHandler.java
│
├── vacancy/                       <-- МОДУЛЬ 1: Вакансії та компанії
├── recruitment/                   <-- МОДУЛЬ 2: Заявки та воронка статусів
├── assessment/                    <-- МОДУЛЬ 3: ШІ-оцінка, парсинг резюме, фідбек інтерв'ю
└── notification/                  <-- МОДУЛЬ 4: Сповіщення (Email, Telegram)
```

### Головні правила коду всередині модуля:
1. **Проста і зрозуміла структура:** Всередині модуля використовуємо звичайний, прагматичний стек Spring:
   * **`Controller`** (приймає HTTP-запит)
   * **`Service`** (містить бізнес-логіку)
   * **`Repository`** (працює з БД через Spring Data)
   * **`Records`** (для вхідних та вихідних DTO)
2. **Інкапсуляція (`package-private`):**
   * Контролери, публічні DTO та події ми робимо `public` (те, що має бачити зовнішній світ).
   * Сутності бази даних, репозиторії та внутрішні сервіси ми робимо **без слова `public`** (тобто `package-private`). Завдяки цьому Java на рівні компілятора забороняє іншим модулям лізти у внутрішню базу даних модуля!
3. **Автоматична перевірка архітектури:**
   У тестах є один метод:
   ```java
   ApplicationModules.of(CandidAiApplication.class).verify();
   ```
   Якщо хтось випадково імпортує внутрішній клас чужого модуля — тести не пройдуть, білд зламається.

## 3. Як модулі взаємодіють між собою? (Гібридний підхід)

Ми **НЕ** робимо всі виклики через події (`ApplicationEventPublisher`), тому що чистий Event-Driven підхід важко тестувати, у коді зникає видимість того, хто кого викликає, і важко шукати помилки.

Ми використовуємо **здоровий гібридний підхід**:

### А. Прямі виклики через публічний інтерфейс (Синхронно)
Коли одному модулю негайно потрібні дані з іншого:
* Наприклад, модуль `recruitment` перед створенням заявки має перевірити: «Чи існує вакансія з таким `id` і чи вона відкрита?».
* Модуль `vacancy` публікує простий інтерфейс `VacancyApi`:
  ```java
  public interface VacancyApi {
      boolean isVacancyOpen(UUID vacancyId);
  }
  ```
* Сервіс заявок просто інжектить `VacancyApi` через конструктор. Жодної магії, працює `Ctrl+Click`, автодоповнення і звичайні тести з `Mockito`.

### Б. Події Spring Events (Тільки для важких фонових задач)
Події використовуємо **лише** для двох речей:
1. **ШІ-аналіз резюме:** Виклик LLM триває 2–5 секунд. Кандидат не повинен чекати цього у браузері. Після збереження заявки кидається подія `ApplicationSubmittedEvent`, а модуль `assessment` у фоні обробляє файл.
2. **Відправка листів / Telegram:** Якщо сервер пошти тимчасово лежить, це не повинно ламати збереження заявки кандидата.

## 4. Вимоги до ДЗ (Лекція 2: REST API шар)

Кожен ендпоінт, який ми пишемо в рамках цього завдання, повинен відповідати вимогам лекції:
1. **REST-іменування:** Іменники у множині, без дієслів у шляху (`POST /api/v1/vacancies`, а не `/createVacancy`).
2. **Java Records для всіх DTO:** Повна незмінність даних (`public record CreateVacancyRequest(...) {}`). Жодного `@Data` з Lombok для DTO.
3. **Jakarta Validation:** Валідація всіх вхідних полів анотаціями (`@NotBlank`, `@Size`, `@Email`, `@Min`, `@Max`, `@Positive`). Контролер приймає `@Valid @RequestBody ...`.
4. **Суворий Jackson:** У `application.yaml` вмикаємо `fail-on-unknown-properties: true` (якщо клієнт надсилає зайве поле, сервер відхиляє запит із помилкою 400).
5. **Єдиний формат помилок RFC 9457 (`ProblemDetail`):** Помилки валідації та відсутності ресурсу повертаються у стандартному форматі через спільний `@RestControllerAdvice`.
6. **Тести взаємодії:** Базові тести на кожен контролер через `@WebMvcTest` або `MockMvc` (перевірка успішного сценарію `200/201` та сценарію валідації `400 Bad Request`).

## 5. Розподіл завдань між 3 членами команди

Кожен учасник бере на себе **один повноцінний наскрізний бізнес-кейс** (вертикальний слайс):

```
┌────────────────────────────────────────────────────────────────────────┐
│                        CandidAI Web Layer                              │
├───────────────────┬────────────────────────────┬───────────────────────┤
│    Учасник 1      │         Учасник 2          │       Учасник 3       │
│    (Вакансії)     │      (Подання заявки)      │  (Воронка та фідбек)  │
│  Модуль: vacancy  │    Модуль: recruitment     │  Модуль: recruitment  │
├───────────────────┼────────────────────────────┼───────────────────────┤
│ • Створення       │ • Подання заявки           │ • Переведення етапу   │
│ • Перегляд списку │ • Перегляд статусу за ID   │ • Оцінка техліда      │
│ • Деталі та статус│ • Валідація email/телефону │ • Валідація оцінок    │
└───────────────────┴────────────────────────────┴───────────────────────┘
```

---

### 👤 Розробник 1: Управління вакансіями (Кейс Рекрутера)
* **Пакет:** `ua.edu.ukma.candidai.vacancy`
* **Що реалізувати:**
  1. `POST /api/v1/vacancies` — створення вакансії:
     * DTO: `CreateVacancyRequest` (назва, опис, перелік навичок, зарплатна вилка `minSalary`/`maxSalary`).
     * Валідація: `@NotBlank`, `@Size`, `@Positive`.
     * Відповідь: `201 Created` + заголовок `Location` (`/api/v1/vacancies/{id}`).
  2. `GET /api/v1/vacancies` — отримання списку вакансій:
     * Query-параметри: `@RequestParam(defaultValue = "OPEN") VacancyStatus status`, пагінація (`page`, `size`).
  3. `GET /api/v1/vacancies/{id}` — перегляд деталей вакансії (якщо нема — `404 Not Found`).
  4. `PATCH /api/v1/vacancies/{id}/status` — відкриття/закриття вакансії (`OPEN`, `CLOSED`).
* **Тести:** `VacancyControllerTest` (перевірка `201 Created`, перевірка валідації назви `400 Bad Request`, `404 Not Found`).

---

### 👤 Розробник 2: Подання заявки кандидатом (Кейс Кандидата)
* **Пакет:** `ua.edu.ukma.candidai.recruitment` (підпакет або файли подачі заявок)
* **Що реалізувати:**
  1. `POST /api/v1/applications` — надсилання відгуку кандидатом:
     * DTO: `ApplyForVacancyRequest` (`vacancyId`, `candidateName`, `email`, `phone`, `resumeUrl` або текст резюме).
     * Валідація: `@NotNull` для ID, `@NotBlank` для імені, `@Email` для пошти, регулярка для телефону.
     * Відповідь: `201 Created` + `Location` + статус `APPLIED`.
  2. `GET /api/v1/applications/{id}` — отримання поточної картки заявки кандидата:
     * DTO: `ApplicationResponse` (ID, вакансія, ПІБ, email, статус у воронці, дата подання).
* **Тести:** `ApplicationControllerTest` (перевірка створення `201 Created`, перевірка некоректного email `400 Bad Request` зі структурою `ProblemDetail`).

---

### 👤 Розробник 3: Воронка відбору та фідбек співбесіди (Кейс Техліда)
* **Пакет:** `ua.edu.ukma.candidai.recruitment` (або `evaluation`)
* **Що реалізувати:**
  1. `PATCH /api/v1/applications/{id}/status` — переведення заявки на наступний етап:
     * DTO: `UpdateApplicationStatusRequest` (новий статус: `SCREENING`, `INTERVIEW`, `OFFER`, `REJECTED`, причина відмови/коментар).
     * Валідація: `@NotNull`.
     * Відповідь: `200 OK` з оновленим DTO заявки.
  2. `POST /api/v1/applications/{id}/feedbacks` — збереження відгуку після технічного інтерв'ю:
     * DTO: `SubmitInterviewFeedbackRequest` (`interviewerName`, `technicalScore` від 1 до 5, `notes`, `decision`: `HIRE` / `REJECT`).
     * Валідація: `@Min(1) @Max(5)`, `@NotBlank` для нотаток, `@NotNull` для рішення.
     * Відповідь: `201 Created`.
  3. `GET /api/v1/applications/{id}/feedbacks` — перегляд історії оцінок кандидата.
* **Тести:** перевірка успішного додавання фідбеку, перевірка виходу балу за межі 1-5 (`400 Bad Request`), перевірка зміни статусу.

## 6. Спільний фундамент (Робиться ДО того, як розійтися по гілках)

Щоб уникнути будь-яких конфліктів, у базову гілку спочатку додається спільний фундамент:

1. **`application.yaml`:**
   ```yaml
   spring:
     application:
       name: CandidAI
     jackson:
       deserialization:
         fail-on-unknown-properties: true
       default-property-inclusion: non_null
       serialization:
         write-dates-as-timestamps: false
     mvc:
       problem-details:
         enabled: true
   ```

2. **`GlobalExceptionHandler.java` (пакет `ua.edu.ukma.candidai.common.exception`):**
   * Перехоплює `MethodArgumentNotValidException` і збирає всі помилки полів у `ProblemDetail` (RFC 9457).
   * Перехоплює `ResourceNotFoundException` і повертає `404 Not Found` у форматі `ProblemDetail`.

## 7. Git Workflow: Як працюємо з гілками

Щоб процес був ідеальним, а код-рев'ю — легким і прозорим:

```text
main
 │
 └──> feat/web-layer  (Базова гілка веб-шару)
       │
       │─── [Коміт 1: Спільний фундамент: yaml + GlobalExceptionHandler]
       │
       ├───> feat/web-layer-vacancies    (Гілка Розробника 1) ──┐
       ├───> feat/web-layer-applications (Гілка Розробника 2) ──┼──> Pull Requests у feat/web-layer
       └───> feat/web-layer-feedback     (Гілка Розробника 3) ──┘
```

### Покроковий алгоритм:
1. Створюємо гілку `feat/web-layer` від `main`.
2. Заливаємо туди налаштування `application.yaml` та `GlobalExceptionHandler`.
3. Кожен відгалужує свою персональну гілку від `feat/web-layer` (наприклад, `feat/web-layer-vacancies`).
4. Кожен спокійно реалізує свої DTO, контролер, in-memory сховище (або заглушку сервісу) та юніт-тести.
5. Кожен відкриває **Pull Request** у гілку `feat/web-layer`.
6. Робимо швидке взаємне код-рев'ю (перевіряємо, щоб не було Lombok `@Data`, щоб були валідації та тести).
7. Мерджимо всі 3 гілки в `feat/web-layer`.
8. Запускаємо `./gradlew test checkstyle` — переконуємося, що все зелене.
9. Робимо один підсумковий Pull Request із `feat/web-layer` у `main`!
